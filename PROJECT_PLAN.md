# PROJECT_PLAN.md — Корпоративний сайт агрокомпанії

Статус: **Реалізовано.** Фаза 1 (Discovery) і Фази 2–10 (реалізація) завершені — сайт збирається (`pnpm build`), проходить типи (`tsc --noEmit`) і лінт (`pnpm lint`) без помилок. Деталі та відомі застереження — у розділі 12.

## 1. Контекст і вихідні дані

Репозиторій на момент старту — порожній (не ініціалізований git, жодних файлів). Це проєкт "з нуля".

Компанія: агробізнес B2B, три напрямки — ПММ (паливо-мастильні матеріали), насіння, інші рішення (в перспективі). Сайт — **не інтернет-магазин**: без кошика, оплати, особистих кабінетів. Мета — презентація + довіра + генерація лідів через контакт з менеджером.

Ключова вимога, яка визначає майже всі рішення нижче: **сайтом має керувати нетехнічний менеджер** — без Git, Markdown, JSON, HTML.

## 3. Вибір CMS — порівняння

Я розглянув три варіанти, явно згадані в `CLAUDE.md`.

### 3.1 Decap CMS (git-based)
- **Плюси:** повністю безкоштовний, контент зберігається як файли в git (простий бекап/історія), не залежить від зовнішнього SaaS.
- **Мінуси:** редагування пов'язаних сутностей (продукт → категорія → бренд) через `relation` widget незручне й крихке при великій кількості записів; завантаження зображень і медіа-бібліотека слабші за Sanity; кожне збереження — це git commit, що для нетехнічного менеджера є менш інтуїтивним (затримки CI, конфлікти при одночасному редагуванні); reordering (drag-n-drop) для брендів/переваг реалізується гірше.
- Не обрано: не проходить вимогу "менеджер-френдлі" на рівні, який потрібен для каталогу продуктів із категоріями/брендами.

### 3.2 Payload CMS
- **Плюси:** повний контроль, чудовий TypeScript-first DX, локальний хостинг адмінки.
- **Мінуси:** вимагає власної бази даних (Postgres/Mongo) і постійно працюючого Node-сервера для адмін-панелі — це вже не "serverless на Vercel за $0", а окремий сервіс хостингу (Railway/Render тощо), що суперечить п.40 ("no over-engineering") і бажаному $0-хостингу для невеликого корпоративного сайту.
- Не обрано: надлишкова інфраструктурна складність відносно задачі.

### 3.3 Sanity ✅ Обрано
- **Плюси:**
  - Studio вбудовується прямо в Next.js-застосунок на `/studio` — один деплой, без окремого хостингу адмінки.
  - Референси між документами (Product → Category, Product → Brand) — це нативна фіча з валідацією та зручним UI вибору.
  - Масиви з drag-n-drop reordering "з коробки" (для брендів, переваг, статистики, характеристик продукту) — точно те, що описано в п.19, 24.
  - Вбудований image pipeline (кадрування, hotspot, CDN, автоматичний webp/avif) — закриває вимоги п.29 без додаткового коду.
  - Безкоштовний тариф: 3 користувачі, значний ліміт API-запитів/пропускної здатності, 5 ГБ медіа — з запасом для невеликого корпоративного сайту.
  - GROQ + `next-sanity` — офіційна, добре задокументована інтеграція з ISR/on-demand revalidation через вебхуки.
  - Реальний, перевірений UX для нетехнічного редактора: форми з полями, а не JSON/Markdown.
- **Мінуси (усвідомлені компроміси):** залежність від зовнішнього SaaS (є free tier ліміти, малоймовірно що будуть вичерпані на такому трафіку); контент не лежить "у git" (мінімізується регулярним експортом `sanity dataset export`, задокументовано в README).

**Рішення: Sanity CMS**, Studio змонтована за адресою `/studio` в тому ж Next.js-проєкті. Це найкраще закриває п'ятірку критеріїв з `CLAUDE.md` (§7): $0-хостинг, простота, UX для менеджера, SEO, продуктивність, надійність, підтримуваність, масштабованість.

## 4. Контент-модель (Sanity schemas)

Реюзабельні об'єкти:
- `seo` (object): `metaTitle`, `metaDescription`, `ogImage` — вбудовується в кожен document-тип сторінки.
- `cta` (object): `label`, `href`, `style` ('primary' | 'secondary').
- `statValue` (object): `value`, `label`, `suffix?`.
- `socialLink`, `characteristic` — прості пари полів для соцмереж і специфікацій товару.

Документи-синглтони (по одному запису, редагуються як "сторінка"):
- `siteSettings` — назва компанії, логотип, короткий опис (footer), телефон, email, адреса, графік роботи, соцмережі/месенджери (масив `{platform, url}`), юридична інформація, `seo` за замовчуванням.
- `homePage` — `hero {title, subtitle, image, ctaPrimary, ctaSecondary}`, `intro {title, text, image}`, `businessDirections[]` (ref → `businessDirection`), `advantages[]` (ref → `advantage`), `stats[]` (`statValue`), `brandsSectionTitle`, `brands[]` (ref → `brand`), `finalCta {title, text, button}`, `seo`.
- `aboutPage` — `title`, `intro`, `body` (Portable Text), `mainImage`, `advantagesTitle?`, `advantages[]`, `stats[]`, `seo`.
- `contactsPage` — `title`, `intro`, `seo` (контактні дані беруться з `siteSettings`, щоб не дублювати).

Документи-колекції:
- `category` — `title`, `slug`, `image`, `description`, `order` (число, для сортування).
- `brand` — `name`, `logo`, `url?`.
- `advantage` — `title`, `description`.
- `businessDirection` — `title`, `description`, `image`, `cta` (для секції "ПММ / Насіння / Інші рішення").
- `product` — `title`, `slug`, `category` (ref → `category`), `brand` (ref → `brand`, optional), `shortDescription`, `description` (Portable Text), `characteristics[]` (`{label, value}`), `images[]`, `order`, `status` ('active' | 'archived' — архівовані не рендеряться на сайті, але лишаються в CMS), `seo`.
- `newsPost` — `title`, `slug`, `publishedAt`, `excerpt`, `coverImage`, `body` (Portable Text), `seo`. Реалізовано (не тільки заплановано) — `/news` і `/news/[slug]` є в коді.

**Slug-унікальність:** `category.slug` і `product.slug` валідуються на унікальність **між собою** (кастомний `isUnique` у `src/sanity/schemaTypes/isUniqueSlug.ts`, використовується в обох схемах) — необхідна умова для резолвера `/products/[slug]` з розділу 5.

Обмеження полів для менеджера: усі заголовки/описи полів у Studio — українською, з поясненням призначення; `slug` генерується автоматично з `title`; технічні поля (`order`, `status`) мають прості значення (число, select).

## 5. Структура сторінок і маршрутизація

```
/                         → homePage
/about                    → aboutPage
/products                 → список категорій
/products/[slug]          → резолвиться в runtime: спершу шукаємо category зі slug,
                            якщо немає — шукаємо product зі slug
/contacts                 → contactsPage + siteSettings + форма
/news                     → список newsPost
/news/[slug]              → детальна новина
```

**Технічний нюанс, який фіксую свідомо:** у Next.js App Router не можна мати одночасно `/products/[category]/page.tsx` і `/products/[slug]/page.tsx` — це два різні динамічні сегменти на одному рівні шляху, Next.js це забороняє ("You cannot use different slug names for the same dynamic path"). `CLAUDE.md` §9 просить обидва плоскі маршрути одночасно.

Рішення (реалізовано в `src/app/(site)/products/[slug]/page.tsx`): **єдиний динамічний сегмент**, який на сервері спершу перевіряє, чи `slug` належить `category` (`getCategoryBySlug`); якщо так — рендерить сторінку категорії (список продуктів через `getProductsByCategory`), якщо ні — шукає `product` з таким slug (`getProductBySlug`) і рендерить картку товару; якщо не знайдено жодного — `notFound()`. `generateStaticParams` об'єднує слаги категорій і продуктів (`getAllCategoryAndProductSlugs`) для SSG всіх існуючих сторінок наперед; нові/невідомі слаги (наприклад, щойно опублікований товар) все одно рендеряться on-demand, бо `dynamicParams` не вимкнено — це дає ISR-подібну поведінку без окремого налаштування.

## 6. Дизайн-система

**Кольори** (CSS-змінні в `src/app/(site)/globals.css`, підняті в `@theme inline` для Tailwind v4):
- `--color-brand-50…900` (глибокий агрозелений — заголовки, CTA, темні секції)
- `--color-graphite-900/800/700` (темний графіт — окремий від brand-зеленого, для найтемнішого шрому: header при скролі, footer)
- `--color-neutral-50…600` (шкала сірого — текст, бордери, приглушені фони)
- `--color-base-white/-offwhite` (фон)
- `--color-accent-500/600` (стриманий природний зелений акцент — точково: іконки, теги, стан помилки форми; **не** заливка секцій)

**Типографіка:** `next/font/google`, кирилична підмножина (`subsets: ["latin", "cyrillic"]` — критично для українського тексту):
- **Manrope** — заголовки (`--font-heading`).
- **Inter** — текст (`--font-body`).

Шкала фіксується як `--text-display/h1/h2/h3/body-lg/body/caption/button` (простір імен Tailwind v4 — саме `--text-*`, а не `--font-size-*`, перевірено джерелом пакета) з `clamp()` для плавного масштабування.

**Компоненти** (реалізовано за списком §26 з `CLAUDE.md`): `Header`, `Footer`, `Container`, `Section`, `Button`, `Hero`, `ProductCard`, `ProductGrid`, `CategoryCard`, `NewsCard`, `CtaButton` (обгортка над `Button` для CMS-об'єктів `cta`), `Breadcrumbs`, `StatsSection`, `AdvantagesSection`, `SmartImage` (= `ImageBlock` зі списку §26 — єдина точка рендеру зображення, що прозоро перемикається між реальним фото Sanity й згенерованою іконкою-заглушкою), `RichText` (рендер Portable Text для `aboutPage.body`/`product.description`).

**Плейсхолдер-графіка:** поки в CMS немає реальних фотографій, `SmartImage` рендерить `PlaceholderArt` — згенеровану іконку (`lucide-react`) на градієнтному фоні замість фото. Свідоме рішення проти дешевих стокових фото (§ вимога "no cheap stock photos") і проти саморобних SVG (ризик низької якості) — не залежить від зовнішніх мереж, юридично чисте.

**Анімації:** мінімальні CSS-transitions (hover, scroll-стан header) з `prefers-reduced-motion` у `globals.css`; `framer-motion` не додавався — для обсягу анімацій, що реально знадобився, зайва залежність.

## 7. Форма зворотного зв'язку

Реалізовано в `src/app/api/contact/route.ts` + клієнтський `src/components/sections/ContactForm.tsx`:
1. Серверна валідація (Zod, `src/lib/validations/contact.ts`, той самий схема-об'єкт що й на клієнті) — ім'я, телефон/email (хоча б одне), повідомлення.
2. Anti-spam без капчі: honeypot-поле `company` (прихований CSS, `aria-hidden`) + перевірка, що з моменту рендеру форми (`renderedAt`) минуло не менше 3с.
3. Rate limiting на IP — простий in-memory fixed-window лічильник (`src/lib/rate-limit.ts`, 5 запитів/10 хв на "теплий" інстанс). Свідомо задокументоване обмеження підходу: на serverless це ліміт "на інстанс", не глобальний, і скидається на холодному старті — прийнятний компроміс для низькотрафікової B2B-форми; шлях апгрейду до Upstash/Vercel KV описано в коментарі файла, якщо колись знадобиться.
4. Надсилання через **Resend** (`resend.emails.send`, `RESEND_API_KEY`) на `CONTACT_FORM_TO_EMAIL`, `replyTo` = email відвідувача (якщо вказаний).
5. Якщо `RESEND_API_KEY`/адреси не налаштовані — сервер повертає чесний HTTP 503 з проханням зателефонувати, а не мовчки "success" без фактичного надсилання (реальне повідомлення користувача ніколи не повинно тихо губитися).
6. Стани на клієнті: idle → submitting → success/error, повідомлення українською.

Секрети — лише в `.env.local` / Vercel Environment Variables, `.env.example` містить перелік змінних без значень.

## 8. SEO та продуктивність

- `generateMetadata` на кожній сторінці (`/`, `/about`, `/products/[slug]`, `/contacts`, `/news`, `/news/[slug]`) з fallback на `siteSettings.seo`.
- `src/app/sitemap.ts` і `src/app/robots.ts` — генеруються з реального списку категорій/товарів/новин, `/studio` і `/api` закриті в robots.
- JSON-LD: `Organization` (в кореневому layout, з реальних `siteSettings`) + `Product` (на сторінці товару, без вигаданого `offers`/ціни — їх немає насправді).
- Зображення: кастомний `next/image`-loader на CDN Sanity (`src/lib/sanity/image-loader.ts`, `images.loader: "custom"` у `next.config.ts`) — Sanity сам ресайзить/re-encode, без подвійної трансформації через вбудований оптимізатор Next.
- Ревалідація: ISR через `fetch(..., {next: {revalidate: 3600, tags}})` у кожній функції `src/lib/sanity/fetch.ts` + Sanity webhook → `POST /api/revalidate` → `revalidateTag(type, {expire: 0})` на publish, миттєве оновлення без повного редеплою.
- 404: `src/app/global-not-found.tsx` (experimental `globalNotFound`, розділ 12 — чому саме цей механізм).

## 11. Відкриті припущення

- `/news` реалізовано (не лишилось на рівні "опція").
- Пакетний менеджер — pnpm (зафіксовано в `package.json` полем `packageManager`).
- Контактна форма — email через Resend.
- Скрипт `scripts/seed.ts` для наповнення Sanity демо-даними **свідомо не створювався**: `src/lib/demo-content.ts` уже дає повноцінний перегляд сайту без жодного Sanity-проєкту (fallback-шар у `src/lib/sanity/fetch.ts`), а дублювання того самого контенту в окремий seed-скрипт додало б підтримку двох джерел істини без реальної користі. Якщо клієнту знадобиться швидко наповнити реальний Sanity-датасет цим же демо-контентом "для старту" — це окрема, чітко обмежена задача на майбутнє.
- Реальні `SANITY_PROJECT_ID` і продакшн-домен Resend/Vercel потрібні лише на етапі деплою.

## 12. Нотатки з реалізації — версійні пастки Next.js 16 / Sanity 6 (важливо для майбутніх сесій)

Next.js 16 і Sanity Studio 6 виявились сумісні, але з кількома недокументованими для їхньої версійної комбінації нюансами, знайденими лише через реальну збірку (`next build`), а не через читання типів:

1. **`next.config.ts` більше не має ключа `eslint`.** Next.js 16 прибрав команду `next lint` і опцію `eslint.ignoreDuringBuilds` — `next build` взагалі не запускає лінт. Лінт — окремий крок `pnpm lint` (ESLint CLI, flat config, вже налаштовано в `eslint.config.mjs`).
2. **`revalidateTag` тепер вимагає другий аргумент** (`profile: string | {expire?: number}`) — виклик з одним аргументом deprecated. Для вебхука (виклик поза Server Action) правильне значення — `revalidateTag(tag, {expire: 0})` для миттєвого, а не "stale-while-revalidate", інвалідування (див. `src/app/api/revalidate/route.ts`).
3. **`@sanity/icons` v5 прибрав іменовані експорти з кореневого entry-point.** `import {TagIcon} from "@sanity/icons"` резолвиться в тип, але падає в рантаймі — треба `import {TagIcon} from "@sanity/icons/Tag"` (підпуть на кожну іконку). Виправлено в усіх `src/sanity/schemaTypes/documents/*.ts`.
4. **`swr` (транзитивна залежність Sanity Studio UI) ламає RSC-бандлінг Turbopack.** `swr`'s `"react-server"`-умовний експорт не має `default export`, а Studio-код його очікує — падає з "export default doesn't exist" при білді `/studio`. Виправлено через `serverExternalPackages: ["swr", "sanity", "@sanity/vision"]` у `next.config.ts` (ці пакети виконуються тільки в браузері/як "use client", тож нативний Node `require` замість RSC-бандлінгу — безпечний обхід).
5. **Мережеве обмеження цього sandbox-середовища розробки (не код):** `next/font/google` не може завантажити Manrope/Inter, бо вихідний egress-проксі цього середовища блокує `fonts.googleapis.com` (403 policy denial, перевірено напряму через `curl` і статус проксі). Це підтверджено ізольовано: тимчасова заміна викликів `next/font/google` на статичні заглушки (без зміни решти коду) дала **успішний** `next build` з усіма 33 маршрутами (`/`, `/about`, `/products` + 18 SSG-сторінок товарів/категорій, `/news` + 3 SSG-новини, `/contacts`, `/studio`, `sitemap.xml`, `robots.txt`) — після чого реальні імпорти `next/font/google` повернуто назад без змін. На Vercel/GitHub Actions/локальній машині розробника з нормальним доступом в інтернет ця мережева блокировка відсутня і збірка пройде без додаткових дій.

Загальний висновок: жодна з цих пасток не є помилкою в коді проєкту — усі підтверджені прямим читанням встановлених `node_modules` (типів і рантайм-джерела), а не з тренувальних даних, згідно з вимогою "не вигадуй API".

## 13. Двомовність (uk/en) — архітектура та рішення

Додано після затвердження початкової збірки: реальна назва клієнта (ТОВ «ГЛОБАЛ АГРО ІНВЕСТ», замінила демо-плейсхолдер «АгроВектор») та повноцінна англомовна версія сайту з автоматичним перекладом.

**Маршрутизація.** Офіційний патерн Next.js App Router (`app/[lang]` + `proxy.ts`, задокументований у `node_modules/next/dist/docs/01-app/02-guides/internationalization.md`) — без нових залежностей (`next-intl` розглядався, але відхилений: дві реальні несумісності з Next 16 вже траплялись цієї сесії з пакетами, що заявляли підтримку "^16", тож ризик не виправданий для функціоналу, який реалізується вбудованими засобами за прийнятний обсяг коду). Українська — застава за замовчуванням без префіксу (`/products`), англійська — з префіксом (`/en/products`); `src/proxy.ts` переписує `/products` на `/uk/products` лише внутрішньо (URL у адресному рядку не змінюється), решта маршрутів під `src/app/(site)/[locale]/...`.

**Переклад контенту.** Менеджер пише **лише українською** в Sanity — це єдина мова, яку Studio знає. Англійська версія кожного текстового поля перекладається на льоту через Azure AI Translator (`src/lib/translate.ts`) і кешується через `unstable_cache`, з тегами, що збігаються з тегами `src/lib/sanity/fetch.ts` — тобто той самий вебхук `/api/revalidate`, який вже інвалідував кеш контенту, тепер інвалідує й кеш перекладу цього контенту без жодних змін у самому вебхуку. Якщо Azure недоступний або ключ не заданий — переклад "м'яко" не відбувається (показується оригінал українською), сторінка ніколи не падає через недоступність зовнішнього сервісу.

Що перекладається: заголовки, описи, alt-тексти зображень, характеристики товарів, rich-text (Portable Text — по вузлах `span`, зі збереженням структури блоків). Що **навмисно ніколи** не перекладається: назва компанії, назви брендів (власні назви), телефон/email/адреса/юридичний код (факти, а не текст), slugs та href (частина URL). Статичні UI-тексти (кнопки, навігація, форми, повідомлення про помилки) — окремий словник (`src/dictionaries/{uk,en}.ts`), перекладений вручну один раз, а не через Azure на кожен запит: короткий фіксований набір міток вартий одноразового ретельного перекладу.

Кожна англійська сторінка показує непомітну примітку "This page was machine-translated from Ukrainian" (footer) — чесність про походження тексту, узгоджено з клієнтом.

**Що НЕ зроблено (свідомо, малий ризик):** `src/app/global-not-found.tsx` (спеціальний файл поза деревом `[locale]` — Next.js вимагає це для `experimental.globalNotFound`) завжди показує українську версію 404-сторінки. Повна локалізація цього єдиного файлу вимагала б окремого визначення locale з `Accept-Language`/referrer поза звичайним маршрутизатором — не виправдано для сторінки "вас тут не мало бути".
